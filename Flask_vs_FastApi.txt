Důvody, proč je v EasyFlexu použitý Flask a ne FastAPI
=======================================================

Kontext projektu (stručně)
---------------------------
EasyFlex obsahuje webovou vrstvu se šablonami, přihlášením uživatelů a CRUD
workflow kolem nahrávání dokumentů a správy nastavení. Současná aplikace je
postavená na Flasku s Flask-Login a Flask-SQLAlchemy, což silně ovlivňuje
praktickou volbu frameworku.

Proč je Flask pro EasyFlex vhodnější než FastAPI
-----------------------------------------------

1) Integrace a existující ekosystém v projektu
- EasyFlex už používá Flask-Login a Flask-SQLAlchemy. Tyto knihovny jsou
  přirozeně navržené pro Flask a poskytují minimální tření v integraci.
- V EasyFlexu je už hotová webová vrstva, kde Flask funguje jako „tenká“ vrstva
  nad logikou a databází. Přechod na FastAPI by znamenal zásahy do
  autizace, správy session a šablon.

2) Server-rendered UI a šablony
- Flask je tradičně silný v server-rendered HTML (Jinja2), což je vhodné pro
  jednoduché administrativní UI, které EasyFlex potřebuje (přihlášení,
  nastavení, uploady, náhledy, workflow).
- FastAPI je primárně zaměřené na API-first a často se kombinuje s
  front-endem zvlášť (SPA). To by zvyšovalo komplexitu projektu.

3) Jednoduchost, menší kognitivní zátěž
- Flask má velmi přímočarý model: routy, request/response, šablony, session.
  To odpovídá potřebám EasyFlexu, který nepotřebuje komplexní API vrstvy.
- FastAPI přidává koncepty jako Pydantic schémata, deklarativní dependency
  injection, asynchronní flow – to je užitečné u rozsáhlých API, ale pro
  menší webovou vrstvu může být nadbytečné.

4) Existující kód a rychlost vývoje
- V EasyFlexu už existuje funkční Flask app. Změna na FastAPI by znamenala
  čas na refaktoring, testování a přepsání autentizace a session managementu.
- V praxi je rychlejší držet se již osvědčeného řešení, pokud není důvod
  (např. extrémní výkonové požadavky nebo potřeba async API).

5) Autentizace a session management
- Flask-Login poskytuje jednoduchý a stabilní model uživatelských session.
- Ve FastAPI se autentizace obvykle řeší přes externí balíčky nebo vlastní
  implementaci, což zvyšuje náklady na údržbu.

6) Výkon a “rychlost” v kontextu EasyFlexu
- FastAPI je známé vysokým výkonem v API scénářích (uvicorn + async), ale
  pro EasyFlex, kde je hlavní zátěž I/O (upload PDF, práce s daty, přístup
  do DB, integrace s externími službami), není Flask úzkým hrdlem.
- Reálnou latenci často tvoří API volání do ABRA/OpenAI a práce se soubory,
  nikoli samotný framework.

7) Nasazení a provoz
- Flask je jednodušší na nasazení v klasickém WSGI prostředí (gunicorn,
  uWSGI). Je dobře podporovaný v tradičních hosting prostředích.
- FastAPI vyžaduje ASGI server a často speciálnější setup, což je další
  vrstva, která v EasyFlexu není nutná.

8) Stabilita a konzervativní volba
- Flask je dlouhodobě stabilní a predikovatelný. Pro podnikové/workflow
  aplikace s menším týmem bývá stabilita a jednoduchost důležitější než
  nejvyšší možný výkon.

9) Menší integrační rizika
- Přechod na FastAPI by mohl přinést regressi v přihlášení, session,
  kompatibilitě s existujícími šablonami a stávajícím kódem.
- Vývojový čas by se přesunul z „business“ funkcí (import, extrakce dat)
  na infrastrukturu.

Kdy by naopak dávalo smysl zvažovat FastAPI
-------------------------------------------
- Pokud by se EasyFlex začal profilovat jako čisté API bez server-rendered
  UI.
- Pokud by požadavky na paralelní, vysoce výkonné API endpointy dramaticky
  vzrostly (např. mnoho současných klientů).
- Pokud by bylo potřeba intenzivně využívat async I/O napříč celou aplikací.

Shrnutí
-------
Pro EasyFlex je Flask praktičtější volbou, protože odpovídá současnému
architektonickému stylu (server-rendered UI), má přirozené napojení na
používané knihovny (Flask-Login/SQLAlchemy), je jednodušší na provoz i
údržbu a výkonově není slabým místem v reálném workflow. FastAPI by
přineslo vyšší komplexitu bez adekvátního přínosu pro aktuální potřeby.
